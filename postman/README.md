# Проверка TakeToday через Postman

## Запуск
1. Скопируйте .env.example в .env в корне проекта и задайте DB_PASSWORD. Для проверки администратора добавьте ADMIN_EMAIL и ADMIN_PASSWORD (от 10 символов, до 72 байт UTF-8). Не используйте почту существующего покупателя или сотрудника.
2. Если установлен Docker: docker compose up -d. Это запускает PostgreSQL на 5433 и Mailpit. Без Docker настройте собственные PostgreSQL и SMTP через .env; создайте базу taketoday и укажите DB_URL, DB_USER, DB_PASSWORD. Миграции применяются при запуске бэкенда.
3. В PowerShell из корня проекта: .\start-backend.ps1. Нужны Java 17+ и доступ к Maven-зависимостям.
4. Фронтенд для Postman не нужен. Для браузера: .\start-frontend.ps1, сайт http://localhost:5173.
5. Импортируйте TakeToday.postman_collection.json через Import. Откройте Variables коллекции и задайте значения для локального использования. Отключите унаследованную авторизацию: No Auth. Оставьте cookie jar включенным. Используйте localhost во всех запросах, не смешивайте с 127.0.0.1. Переменные активного environment с теми же именами перекрывают переменные коллекции.

## Важное правило
Перед КАЖДЫМ POST выполняйте запрос 01 (CSRF). Скрипт сохранит csrfToken, POST передаст его в X-CSRF-TOKEN. Postman должен сохранить и отправить cookie JSESSIONID. После verify и logout сессия меняется: обязательно снова выполнить 01. Не запускайте коллекцию целиком через Runner: нужны ручные коды, разные роли и ожидание.

Коды смотрите в http://localhost:8025 (Mailpit) или реальном почтовом ящике при настроенном SMTP. В Variables коллекции вручную установите code как строку из шести цифр, сохранив начальные нули. Новый challenge автоматически очищает старую переменную code. Mailpit перехватывает письма для любых адресов, поэтому не доказывает существование реального ящика. Для этого нужен реальный SMTP и получение кода адресатом.

## Покупатель
1. Задайте email уникальным, например customer-test-01@example.com; password=StrongPassword123; expectedRole=CUSTOMER.
2. Выполните 02 и 03: HTTP 200, роль GUEST. Выполните 11: HTTP 401.
3. 01 → 04: HTTP 200 и challengeId; аккаунт еще не авторизован.
4. Снова 02 и 11: GUEST и 401. Это проверяет обязательность второго фактора.
5. Возьмите код из письма, задайте code, выполните 01 → 05: HTTP 200, CUSTOMER.
6. Выполните 02, 06, 07: CUSTOMER, HTTP 200, HTTP 403.
7. 01 → 08: HTTP 400 — использованный код не принимается.
8. 01 → 09: HTTP 204. Затем 10 и 11: GUEST и HTTP 401.
9. Подождите минимум 60 секунд от последнего отправленного письма. 01 → 12: HTTP 200 и новый challengeId. До проверки кода 02 возвращает GUEST. Введите новый code, затем 01 → 05 и 06.

## Сотрудник
1. Выйдите: 01 → 09. Задайте другой уникальный email и expectedRole=STAFF.
2. 01 → 16. Введите код нового письма, затем 01 → 05.
3. 17: HTTP 200, данные Тестовой пекарни. 06 и /api/admin/home должны вернуть HTTP 403 (встроенные тесты 06 и 18 ожидают 200 для соответствующих ролей; здесь проверяйте 403 вручную).
4. Для проверки изоляции зарегистрируйте еще одного сотрудника с новой почтой и другим названием заведения; /api/staff/home должен вернуть только его заведение. Перед сменой аккаунта выйдите.

## Администратор
1. Создается при старте бэкенда из ADMIN_EMAIL и ADMIN_PASSWORD; публичная регистрация запрещена. Для уже существующего администратора изменение ADMIN_PASSWORD в .env не меняет пароль автоматически.
2. Выйдите, задайте email/password администратора, expectedRole=ADMIN.
3. 01 → 12, введите код из письма, 01 → 05, затем 18: HTTP 200. Для /api/customer/home и /api/staff/home ожидается 403.

## Восстановление пароля
1. Выйдите и верните email покупателя. Подождите 60 секунд после последнего письма.
2. 01 → 13. Введите полученный code, задайте newPassword, затем 01 → 14: HTTP 200.
3. 01 → 12 со старым password: HTTP 401 (тест запроса 12 ожидает 200, здесь смотрите статус вручную).
4. Измените password на значение newPassword; подождите 60 секунд после письма восстановления. 01 → 12, новый code, 01 → 05: успешный вход. expectedRole должен быть CUSTOMER.
5. Для проверки отзыва прежней сессии можно сохранить вход покупателя в другом клиенте/браузере до сброса. После сброса запрос /api/customer/home из прежней сессии должен вернуть 401.

## Ошибки и ограничения
Перед каждым POST выполняйте 01.
- 19 с email уже существующего покупателя: 409.
- 20: 400 — ADMIN нельзя зарегистрировать публично.
- 21 с email существующего аккаунта: 401.
- 22: 400 — некорректный email.
- Неверный код: создайте новый challenge, в запросе 05 введите заведомо другой шестизначный code. Ожидается 400. После пяти ошибок правильный код тоже возвращает 400; начните вход заново.
- Повторная отправка: сразу после получения challenge запрос 15 дает 429; спустя 60 секунд — 200 и новый challengeId. Введите код нового письма, подтвердите через 05. Старый challenge и код больше не работают.
- Срок кода: через 10 минут запрос 05 должен вернуть 400.
- CSRF: удалите заголовок X-CSRF-TOKEN у POST /api/auth/login. Ожидается 403. Верните заголовок и обновите токен через 01.
- Лимит входа: используйте отдельную почту для этой проверки; после 10 запросов регистрации/входа/восстановления/повторной отправки в текущем 15-минутном окне следующие попытки возвращают 429. Успешное подтверждение входа сбрасывает счетчик. Для остальных сценариев дождитесь окончания окна или используйте новую почту.

## Скрипты (уже встроены в коллекцию, вкладка Scripts → Post-response)
Сохранение CSRF:
~~~javascript
pm.test('HTTP 200', () => pm.response.to.have.status(200));
pm.collectionVariables.set('csrfToken', pm.response.json().token);
~~~
Сохранение challenge после register/login/forgot-password/resend:
~~~javascript
pm.test('HTTP 200', () => pm.response.to.have.status(200));
pm.collectionVariables.set('challengeId', pm.response.json().challengeId);
pm.collectionVariables.unset('code');
~~~
Проверка роли после verify:
~~~javascript
pm.test('HTTP 200', () => pm.response.to.have.status(200));
pm.test('Роль', () => pm.expect(pm.response.json().role)
  .to.eql(pm.collectionVariables.get('expectedRole')));
~~~
Проверка ожидаемой ошибки (пример):
~~~javascript
pm.test('Доступ запрещен', () => pm.response.to.have.status(403));
~~~

## Диагностика
- Connection refused: бэкенд не запущен или baseUrl/PORT неверен.
- 503 при отправке кода: проверьте доступность SMTP/Mailpit и настройки .env.
- 403 у POST: обновите CSRF, проверьте заголовок и cookie jar.
- 401 после verify: убедитесь, что Postman сохранил новый JSESSIONID.
- 409 при повторном прогоне: используйте другую почту; данные сохраняются в PostgreSQL.
- 429: соблюдайте паузу 60 секунд между письмами и лимит попыток.

Покупки пока не реализованы. Можно проверить запрет гостевого доступа к защищенным маршрутам, но нельзя проверить успешное приобретение набора на этом этапе.
