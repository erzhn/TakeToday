# Переход на общий порядок миграций

В разных ветках номер V11 использовался для разных изменений. Общий порядок:

| Версия | Миграция |
| --- | --- |
| 10 | `V10__pickup_issue.java` |
| 11 | `V11__optional_two_factor.sql` |
| 12 | `V12__refunds_and_admin.sql` |
| 13 | `V13__offer_archive.sql` |

V11 восстановлена из `d416c60` без изменения SQL (checksum `-2026218794`).
Содержимое миграций возвратов и архива сохранено; изменены только имена файлов.
Упоминание V11 в комментарии миграции архива относится к прежней нумерации.
Столбец `two_factor_enabled` сохраняет совместимость схемы со старой веткой;
в профиле доступно включение/выключение 2FA. По умолчанию вход выполняется по
email и паролю; при включённой 2FA дополнительно требуется код из письма.

## Перед обновлением

Остановить приложение и сохранить незакоммиченные изменения. После публикации
исправления обновить `develop` через `git pull --ff-only origin develop`.
Проверить `DB_URL` и `DB_USER`: локальный PostgreSQL обычно использует порт 5432,
Docker проекта — 5433. Сохранить резервную копию нужных данных.

В своей БД выполнить только запрос:

```sql
SELECT version, description, checksum, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

Дальнейшее действие зависит от фактической истории:

- Новая пустая БД или история до V10: применить миграции обычным запуском.
- Последняя успешная миграция — V11 `optional two factor` с checksum
  `-2026218794`: V12 и V13 должны примениться обычным запуском без очистки данных.
- Применена V11 `refunds and admin` или V12 `offer archive`: автоматическое
  обновление с новой нумерацией не подходит. Сначала отдельно согласовать переход
  с учётом данных. Не выполнять `repair`, не удалять одну лишь историю Flyway и
  не запускать переименованные миграции поверх уже созданных ими объектов.
- Неизвестная история, другой checksum или неуспешная миграция: сначала разобрать
  расхождение, не сбрасывать историю автоматически.

Если согласована очистка локальных данных, сохраняется сама БД `taketoday`, её
владелец и настройки подключения. Состав удаляемых объектов приложения проверяется
отдельно; посторонние объекты не затрагиваются. Этот документ не выполняет очистку.

## Сборка и проверка

После переключения веток обязательно выполнить из корня проекта:

```powershell
.\mvnw.cmd clean test
```

`clean` удалит старые копии миграций из `target`, которые могли остаться от другой
ветки. Затем запустить приложение своей обычной конфигурацией. Проверить успешные
V11/V12/V13 в истории Flyway и открытие сайта.

`MigrationCompatibilityTests` проверяет чистую установку, повторный запуск и
обновление с V11 с сохранением учётной записи и значения `two_factor_enabled`.
По умолчанию используется H2. Для отдельного тестового PostgreSQL можно передать
`migration.test.url`, `migration.test.user`, `migration.test.password` как свойства
Maven. Каждый тест создаёт и удаляет собственную уникальную схему `migration_test_*`.
Для такого запуска использовать только отдельную тестовую БД.

## Слияние веток

Исправление подготовлено от `develop`, без слияния старой реализации возвратов и
админ-панели. Старую функциональную ветку нельзя считать автоматически совместимой:
её изменения нужно отдельно сравнить с текущей реализацией перед переносом.
После включения исправления новые миграции должны получать свободные номера после
V13; перед PR сверить актуальную `origin/develop`, включая Java-миграции. Уже
применённые миграции не редактировать. Отсутствие конфликтов с текущей `develop`
не гарантирует отсутствие конфликтов с будущими изменениями команды.
