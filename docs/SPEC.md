## 1. Словарь

Чтобы называть вещи одинаково — и в разговоре, и в коде.

| Слово | Что значит | В коде |
|---|---|---|
| Заведение | Кафе, пекарня, ресторан | `Establishment` (таблица `establishments`) |
| Предложение / набор | То, что заведение выставило на продажу: «Набор выпечки на вечер» | `Offer` |
| Порция | Одна единица набора. В предложении может быть 5 порций | `portions` |
| Бронь | Порция временно закреплена за покупателем на 3 минуты, пока он платит | заказ в статусе `PENDING_PAYMENT` |
| Заказ | Покупка одной порции одним покупателем | `Order` |
| Платёж | Одна попытка оплаты заказа. У заказа может быть несколько попыток | `Payment` |
| Возврат | Возврат денег за оплаченный заказ | `Refund` |
| Код получения | 6 цифр, которые покупатель показывает сотруднику. Он же в QR-коде | `pickupCode` |
| Окно выдачи | Время, когда можно забрать: с 19:00 до 21:00 | `pickupStart`, `pickupEnd` |

**Один заказ = одна порция.** Если покупатель хочет две — оформляет два заказа. Так проще и соответствует ТЗ (раздел 6 — «бронирование одного набора»).

## 2. Роли и что они могут

| Роль | Код роли | Что может |
|---|---|---|
| Гость (не вошёл) | — | Смотреть каталог и страницу набора, регистрироваться, входить |
| Покупатель | `CUSTOMER` | Всё, что гость + бронировать, платить, видеть свои заказы и код, отменять заказ, менять свои данные |
| Сотрудник заведения | `STAFF` | Менять сведения о своём заведении, создавать/менять/снимать предложения, проверять коды и выдавать заказы, видеть заказы своего заведения |
| Администратор | `ADMIN` | Видеть всех пользователей, заведения, предложения, платежи и возвраты; блокировать учётки, скрывать предложения, оформлять возврат вручную |

**Договорённости:**
- Один сотрудник = одно заведение. Заведение привязано к учётной записи полем `establishments.owner_id` (уникальное).
- Администратора нельзя зарегистрировать через сайт. Он создаётся при запуске из `ADMIN_EMAIL` / `ADMIN_PASSWORD` (`AdminBootstrap`, Жаныбек).
- Сотрудник видит и меняет **только своё** заведение, свои предложения и заказы своего заведения. Проверять это нужно в сервисе, а не только скрывать кнопки (п. 5.2.3).

## 3. Как устроен проект

**Стек:** Java 17, Spring Boot 3.5, Spring Security, JdbcTemplate (SQL-запросы без JPA-сущностей), PostgreSQL, Flyway.
Интерфейс: главная, вход и регистрация — одна страница `static/index.html` + `app.js` (Жаныбек, адреса через `#login`, `#register`, `#code`);
кабинеты (`/profile`, `/staff/**`, `/admin/**`) — страницы Thymeleaf в `templates/` со стилями `static/css/app.css` (Эржан, по макету Figma).

**Пакеты** (`src/main/java/com/example/taketoday/`):

```
auth/          регистрация, вход по коду из письма, сессии, SecurityConfig   Жаныбек ✅
common/        текущий пользователь, правила полей, загрузка файлов, время   Эржан ✅ (общий)
profile/       личный кабинет                                               Эржан ✅
venue/         заведение и его сведения, кабинет сотрудника                 Эржан ✅
admin/         админ-панель                                                 Эржан (обзор ✅, остальное — этап 5)
offer/         предложения                                                  Эржан (этап 2)
catalog/       каталог, поиск, страница набора                              Жаныбек
order/         заказы, бронь, история                                       Жаныбек
payment/       платежи, учебная платёжная служба, код                       Эржан
pickup/        проверка кода и выдача                                       Эржан
refund/        отмена и возврат                                             Эржан
notification/  письма                                                       Жаныбек
scheduler/     фоновые задачи                                               Жаныбек
audit/         журнал событий (п. 5.3.4)                                    общий
```

Внутри пакета: `XxxController` (страницы), `XxxService` (логика), `XxxRepository` (SQL через `JdbcTemplate`), `record` для строк таблиц, `dto/` для форм. Идентификаторы — `UUID`.

**Правила кода:**
- Логика — в сервисах. Контроллер только принимает форму, вызывает сервис и выбирает страницу.
- Проверка «это твоё заведение / твой заказ» — в сервисе.
- Все тексты, которые видит пользователь, — на русском.
- Деньги храним **целыми сомами** (`int`). Копеек нет.
- Время храним в UTC (`Instant` / `timestamptz`), показываем по Бишкеку (`Asia/Bishkek`). Константа: `AppTime.ZONE`.

**Миграции базы (Flyway) — чтобы не конфликтовать:**
- Нумерация подряд: `V1__users.sql`, `V2__authentication.sql` (Жаныбек), `V3__profile_and_establishment_details.sql` (Эржан, этап 1). Следующий номер — `V4`.
- **Перед созданием миграции пишем в чат «беру V4»**, чтобы у нас не было двух файлов с одним номером.
- Уже влитую в `develop` миграцию **никогда не меняем** — только новая миграция. `V1__users.sql` не удаляем: она уже применена в базах.
- Пишем только такой SQL, который понимает и PostgreSQL, и H2 (на H2 идут тесты). Например, нельзя частичные индексы `... WHERE status = 'PAID'`.

### 5.3 `offers` — предложения ✅ (таблица — Жаныбек, V5; кабинет заведения — Эржан)

Схема — `V5__offers.sql`, полное описание полей — в README («Каталог и база предложений»). Вторую таблицу не создаём.

- `photo_path` хранит **адрес картинки целиком**: `/uploads/offers/<uuid>.jpg` — загруженные сотрудником, `/images/offers/*.jpg` — демо-фото.

## 6. Жизнь заказа: статусы и переходы

| Код | Как показываем | Цвет значка |
|---|---|---|
| `PENDING_PAYMENT` | Ожидает оплаты | жёлтый |
| `PAID` | Оплачен | зелёный |
| `ISSUED` | Заказ выдан | серо-синий |
| `CANCELLED` | Отменен | красный |
| `PICKUP_EXPIRED` | Время получения истекло | серый |

Дополнительно у заказа есть **статус возврата** (`refund_status`), который показываем отдельным значком: «Возврат оформлен», «Деньги возвращены», «Ошибка возврата».

```
                 нажал «Оплатить и забронировать»
                              │
                              ▼
                     ┌─────────────────┐
         3 мин без   │ PENDING_PAYMENT │  ошибка оплаты → остаётся тут,
         оплаты ┌────│ Ожидает оплаты  │  можно повторить, пока идут 3 мин
                │    └────────┬────────┘
                ▼             │ платёжная служба: «успешно»
        ┌─────────────┐       ▼
        │  CANCELLED  │  ┌─────────┐   сотрудник подтвердил   ┌────────┐
        │  Отменен    │◄─│  PAID   │─────────────────────────►│ ISSUED │
        └─────────────┘  │ Оплачен │                          │ Выдан  │
         ▲   отмена      └────┬────┘                          └────────┘
         │   покупателем      │ прошло pickup_end, не забрал
         │   до pickup_start  ▼
         │   / заведение ┌────────────────┐
         │   не может    │ PICKUP_EXPIRED │
         │   / админ     │ Время истекло  │
         └───────────────┴────────────────┘
```

**Таблица переходов — кто и когда:**

| Из | В | Когда | Кто делает (код) | Что ещё происходит |
|---|---|---|---|---|
| — | `PENDING_PAYMENT` | Покупатель нажал «Оплатить и забронировать» | Жаныбек `OrderService.reserve` | `reserved_portions + 1`, `reserved_until = now + 3 мин` |
| `PENDING_PAYMENT` | `CANCELLED` (`RESERVATION_EXPIRED`) | `reserved_until` прошло, оплаты нет | Жаныбек, планировщик | `reserved_portions − 1` |
| `PENDING_PAYMENT` | `CANCELLED` (`CUSTOMER`) | Покупатель нажал «Отменить бронь» на странице оформления | Жаныбек | `reserved_portions − 1` |
| `PENDING_PAYMENT` | `PAID` | Пришло «успешно» от платёжной службы, бронь ещё действует | Эржан `PaymentService` → Жаныбек `OrderService.markPaid` | `reserved − 1`, `sold + 1`, создаётся код, письмо с чеком |
| `CANCELLED` (бронь истекла) | — (остаётся `CANCELLED`, причина `LATE_PAYMENT`) | «Успешно» пришло после снятия брони и порций уже нет (п. 4.6.5) | Эржан | Автовозврат денег, письмо |
| `PAID` | `ISSUED` | Сотрудник подтвердил выдачу | Эржан `PickupService` | `issued_at`, `issued_by`, журнал |
| `PAID` | `CANCELLED` (`CUSTOMER`) | Покупатель отменил **до `pickup_start`** | Эржан `RefundService` | `sold − 1` (порция возвращается в продажу, если ещё не `pickup_end`), автовозврат, письмо |
| `PAID` | `CANCELLED` (`VENUE`/`ADMIN`) | Заведение не может выдать / админ отменил | Эржан | Возврат (авто или админ), письмо |
| `PAID` | `PICKUP_EXPIRED` | `pickup_end` прошло, заказ не выдан | Жаныбек, планировщик | Деньги **не** возвращаются |

**Любой другой переход запрещён.** Например, `ISSUED` → что-либо — нельзя. Метод должен бросить исключение с понятным текстом.

**Поздняя оплата (п. 4.6.5), подробно:** если «успешно» пришло, а заказ уже `CANCELLED (RESERVATION_EXPIRED)`:
- если у предложения ещё есть свободная порция и время выдачи не прошло — можно не возвращать деньги, а восстановить заказ (`sold + 1`, статус `PAID`). **Решение: так НЕ делаем** — проще и честнее по ТЗ всегда возвращать деньги;
- меняем `cancel_reason` на `LATE_PAYMENT`, создаём `Refund(AUTO)`, пишем в журнал, отправляем письмо «Оплата пришла после окончания брони, деньги будут возвращены».

## 7. Учёт порций и защита от двойной продажи

Владелец — **Жаныбек**. Это самое важное место проекта (п. 4.5.3, 5.1.2).

**Бронь делается одним SQL-запросом, который сам проверяет остаток:**

```sql
UPDATE offers
SET reserved_portions = reserved_portions + 1, updated_at = now()
WHERE id = :offerId
  AND status = 'ACTIVE'
  AND pickup_end > now()
  AND total_portions - reserved_portions - sold_portions > 0
```

- Если обновилась 1 строка — порция наша, создаём заказ.
- Если 0 строк — порций нет, показываем «Порции закончились».
- База сама выполняет такие запросы по очереди, поэтому из 100 одновременных попыток последнюю порцию получит ровно один.
- Метод `reserve` помечен `@Transactional`: обновление порций и создание заказа — вместе или никак.

**Все изменения счётчиков порций — только через методы `OfferService`** (Эржан даёт, раздел 13):
`tryReserve(offerId)`, `releaseReserved(offerId)`, `confirmSold(offerId)` (reserved − 1, sold + 1), `returnSold(offerId)`.
Каждый — один `UPDATE` с условием, как выше. Напрямую счётчики в других местах не трогаем.

**Изменение количества порций сотрудником (п. 4.4.2):** новое `total_portions` не может быть меньше `reserved_portions + sold_portions`. Проверка в том же `UPDATE ... WHERE`.

**Тест обязателен:** 100 потоков пытаются забронировать предложение с 1 порцией → ровно 1 заказ (Жаныбек, этап 3).

## 8. Оплата (учебная платёжная служба)

Владелец — **Эржан**. Настоящий эквайринг в учебном проекте не подключаем — делаем **учебную платёжную службу** внутри нашего же приложения, которая ведёт себя как настоящая. Так её и называем на защите.

**Устройство:**

```java
public interface PaymentGateway {
    // Создать платёж, вернуть адрес страницы оплаты
    PaymentRedirect createPayment(Payment payment);
}
```

Реализация `MockPaymentGateway` (пакет `payment.mock`). Если когда-нибудь понадобится настоящая служба — пишем вторую реализацию, остальной код не меняется.

**Как идёт оплата:**

1. На странице оформления (`/checkout/{orderId}`) покупатель жмёт «Перейти к оплате».
2. `POST /checkout/{orderId}/pay` (Эржан): проверяем, что заказ его, статус `PENDING_PAYMENT`, бронь не истекла. Создаём `Payment(CREATED)` с `provider_payment_id = UUID`. Перенаправляем на страницу учебной службы.
3. `GET /mock-pay/{providerPaymentId}` — страница «платёжной службы»: форма карты (номер, срок, CVV), логотипы Visa/Mastercard, сумма, кнопка «Оплатить».
   - Карта `4242 4242 4242 4242` — успех.
   - Карта `4000 0000 0000 0002` — отказ «Недостаточно средств».
   - Любой номер не по алгоритму Луна — «Неверный номер карты».
   - Данные карты **не сохраняем**, только последние 4 цифры.
4. Служба «сообщает результат» нашему сайту: `POST /payments/callback` с `providerPaymentId`, `status`, `last4`, `error`. (В учебной версии служба вызывает метод напрямую, но через тот же `PaymentCallbackService.handle(...)`, что и настоящий callback.)
5. `PaymentCallbackService.handle`:
   - Ищем платёж по `provider_payment_id`. Если уже `SUCCEEDED`/`FAILED` — **ничего не делаем** (повторное сообщение, п. 5.3.2), пишем `PAYMENT_DUPLICATE` в журнал.
   - `FAILED` → платёж `FAILED`, заказ остаётся `PENDING_PAYMENT`. Покупателя возвращаем на `/checkout/{orderId}` с ошибкой «Оплата не прошла…» и кнопкой «Повторить оплату» (п. 4.6.3) — пока идут 3 минуты.
   - `SUCCEEDED` и заказ `PENDING_PAYMENT` → вызываем `OrderService.markPaid(orderId)` (Жаныбек), создаём код (раздел 9), `NotificationService.sendPaymentConfirmation(order)` (Жаныбек). Покупателя ведём на `/orders/{orderId}`.
   - `SUCCEEDED`, а заказ уже `CANCELLED` → поздняя оплата, раздел 6.
6. Если служба «недоступна» (для демонстрации — настройка `app.payment.mock.available=false`) — на шаге 2 показываем «Платёжная служба временно недоступна. Попробуйте ещё раз через минуту» (п. 5.3.3).

**Время:** проверка наличия и запуск оплаты — до 0,3 с (п. 5.1.1). Учебная служба отвечает мгновенно, главное — не делать лишних запросов к базе.

**✅ Как сделано на этапе 3 (Эржан)** — с учётом брони Жаныбека (`reservation_orders`, статус `AWAITING_PAYMENT`, страница `/reservations/{id}`):

| Что | Где |
|---|---|
| Кнопка «Перейти к оплате — N сом», ошибка оплаты и «Попробовать оплатить ещё раз» | `reservation/checkout.html` (страница Жаныбека), `POST /reservations/{id}/pay` → `OrderController` |
| Начало оплаты: проверка владельца и срока брони, сумма только из заказа, старая незавершённая попытка → `CANCELLED` | `PaymentService.start` |
| Учебная служба (без логотипов настоящих брендов), Луна, срок ММ/ГГ, CVV, кнопка «Отменить оплату» | `MockPaymentGateway`, `MockPaymentController`, `MockCard`, `payment/mock-pay.html` |
| Результат оплаты (как уведомление банка): сначала `FOR UPDATE` строки `offers`, потом платежа; повтор → `PAYMENT_DUPLICATE`; успех → `PAID`, код, `reserved −= q`, `sold += q`; после срока → `CANCELLED / LATE_PAYMENT`, `refund_status = PENDING` | `PaymentService.complete` |

## 9. Код получения и QR-код

Владелец — **Эржан**.

- Код создаётся **только** при переходе в `PAID` (п. 4.7.1).
- 6 цифр, `SecureRandom`, от `000000` до `999999`, храним строкой (ведущие нули важны).
- Код должен быть уникален среди заказов в статусе `PAID`. Проверяем в сервисе: сгенерировали → есть ли такой `PAID` → если есть, генерируем заново.
- Показ: крупно двумя группами `482 913`.
- **QR-код** содержит просто 6 цифр кода. Генерация на сервере — библиотека ZXing (`com.google.zxing:core` + `javase`), отдаём картинкой: `GET /orders/{id}/qr.png` (доступ только владельцу заказа).
- **Сканирование** у сотрудника: JS-библиотека `html5-qrcode` на странице `/staff/pickup`. Камера в браузере работает только на `https://` или `localhost` — для демонстрации с телефона нужен https (решим на этапе 4).
- Если камера запрещена — поле ручного ввода всегда есть на странице (п. 5.4.3).
- Код виден только самому покупателю и сотруднику заведения при проверке (п. 5.2.5). В письме код есть (п. 4.9.1).

**Проверка кода сотрудником (`PickupService.check(code, staffUser)`)** — порядок проверок и тексты отказа (п. 4.7.4, 4.7.5):

| Проверка | Текст ошибки |
|---|---|
| Код из 6 цифр | «Введите 6 цифр кода» |
| Заказ с таким кодом найден | «Код не найден. Проверьте цифры» |
| Заказ принадлежит заведению сотрудника | «Этот заказ из другого заведения» |
| Статус `ISSUED` | «Заказ уже выдан {дата время}» |
| Статус `CANCELLED` | «Заказ отменен» |
| Статус `PICKUP_EXPIRED` или сейчас > `pickup_end` | «Время получения истекло» |
| Статус не `PAID` | «Заказ не оплачен» |

**✅ Как сделано на этапе 3 (Эржан):** код — `PickupCodeGenerator` (уникален среди `PAID`), QR — `GET /orders/{id}/qr.png` (только ZXing `core` + `ImageIO`, без `javase`; `Cache-Control: no-store`). В QR зашито `TAKETODAY:{orderId}:{код}` — сотрудник на этапе 4 сразу видит нужный заказ. Страница `/orders/{id}` (экран 4) — `orders/detail.html`; чужой заказ → 404, сотрудник → 403, неоплаченный → перенаправление на `/reservations/{id}`.

Подтверждение выдачи — отдельный `POST /staff/pickup/{orderId}/confirm`. Внутри снова все проверки + смена статуса через `UPDATE orders SET status='ISSUED' ... WHERE id=? AND status='PAID'`. Повторное нажатие кнопки ничего не сломает: второй раз обновится 0 строк → «Заказ уже выдан» (п. 5.3.2).
