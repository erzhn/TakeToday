# Бронирование порций

Реализованы пункты 4.5.1–4.5.4 ТЗ. Кнопка в карточке набора создает заказ «Ожидает оплаты» на 180 секунд и открывает `/reservations/{id}`. Эта страница показывает снимки цены, адреса, времени выдачи и серверный срок брони. После перезагрузки срок не начинается заново. Реальный прием платежей не подключен, тестовой кнопки успешной оплаты нет.

`POST /api/orders/reservations`: JSON `{offerId, requestKey, quantity}`, первые два значения UUID, quantity — обязательное положительное целое число. Нужны сессия покупателя и CSRF-токен из `/api/auth/csrf`. Клиент сохраняет requestKey и количество при повторной отправке после сетевой ошибки: сервер вернет тот же заказ вместо повторного резервирования. Повтор ключа с другим количеством отклоняется. Для новой покупки нужен новый ключ.

`GET /api/orders/reservations/{id}` возвращает `{order, serverNow}` только владельцу. Чужой заказ дает 404, сотрудник и администратор не могут создавать или открывать брони покупателя. Клиентские сумма, срок, покупатель и состояние не принимаются.

Миграция V6 добавляет `reservation_orders`; V7 добавляет quantity и unit_price. Старые заказы сохраняются как одна порция с прежней ценой. amount — общая сумма, рассчитанная сервером как quantity × unit_price; цена сохраняется снимком. При создании блокируется строка offers через SELECT FOR UPDATE, проверяются статус, срок выдачи, владелец заведения и наличие всего выбранного количества. Заказ и увеличение reserved_portions на quantity сохраняются в одной транзакции. При истечении срока освобождается сумма quantity просроченных заказов. Общий остаток каталога уже учитывает reserved_portions.

Просроченные неоплаченные заказы переходят в CANCELLED, reserved_portions уменьшается в той же транзакции. Проверка запускается каждые 5 секунд, а также при открытии состояния заказа и новом бронировании того же набора. Повторный запуск безопасен. Без открытого браузера и после перезапуска сервера бронь также снимается. До следующей фоновой проверки каталог может показывать уменьшенный остаток до 5 секунд; новая покупка освобождает просроченную бронь сразу.

## Подключение будущей оплаты

`PAID` зарезервирован в схеме для интеграции платежей. Сейчас ни один публичный маршрут не может установить это состояние. Подтверждение оплаты должно проверять полную сумму amount, блокировать ту же строку offers, затем повторно читать заказ и проверять expires_at по серверному времени. До истечения срока необходимо атомарно заменить AWAITING_PAYMENT на PAID, уменьшить reserved_portions и увеличить sold_portions на quantity. Повторное подтверждение не меняет счетчики. Фоновая задача не освобождает PAID.

Если expires_at уже наступил, нельзя просто поставить PAID: сначала снимается временная бронь, затем обрабатывается поздняя оплата по пункту 4.6.5 ТЗ. При отсутствии порции заказ не подтверждается и требуется возврат. Платежи, возвраты, код получения и QR-код относятся к следующим частям разработки.

## Проверка

`./mvnw.cmd test` выполняет интеграционные проверки без внешней почты на H2, включая 100 одновременных попыток забронировать последнюю порцию. Для проверки на отдельной PostgreSQL можно передать `-Dreservation.test.url`, `-Dreservation.test.user`, `-Dreservation.test.password`, `-Dreservation.test.driver=org.postgresql.Driver` и `-Dtest=ReservationTests`. Используйте только отдельную тестовую базу: тесты создают и удаляют свои записи.

Порог 0,3 секунды из пункта 5.1.1 требует отдельного измерения на целевой инфраструктуре; обычные интеграционные тесты его не доказывают.

При проверке полного набора существующий `CatalogTests.guestCanRenderCatalogAndDetailsWithDatabaseValues` ожидает старый заголовок «Хорошая еда ждёт вас», тогда как текущий шаблон каталога показывает «Вкусная еда со скидкой». Этот тест и заголовок не изменялись в рамках бронирования.
